# P0-04–06 — resilient guest commerce

This slice builds on the retained, verified P0-02–03 candidate. Both are local and awaiting publication approval; the known live Site remains version10. No real payment or delivery integration is introduced.

## Cart and concurrency

`GET /api/shop` retains `items:[{product,qty}]` and adds a monotonic version, server quote, issues and guest-session status. Legacy absolute updates and qty0 removal remain compatible. New clients submit the expected cart version and an operation idempotency key. Successful mutations return a canonical snapshot; replay recovers the result without repeating the effect. Stale revisions require review. A per-tab client queue, read invalidation and session-free BroadcastChannel/storage signals keep the page and other tabs reconciled.

Cart removal offers an eight-second undo anchored to the accepted revision, so it cannot silently overwrite newer changes. Clear-cart requires a modal confirmation; failed clear closes the modal to expose recovery controls. Failed writes retain confirmed state and an explicit retry reuses its operation key. Unknown/unavailable cart rows can be removed safely.

Guest-to-authenticated merge remains a P1 policy: combine matching product/variant IDs within quantity and stock bounds, then require review for conflicts. Authentication is not implemented.

## Coupon contract

One code is persisted for the guest cart. Server calculations use actual cart data, with integer paise internally and the established whole-rupee percentage rounding. Client-supplied totals and clock values are not authoritative. Validation consumes no redemption; successful order creation consumes atomically. Invalid replacement preserves the prior code.

| Code | Rule |
| --- | --- |
| EVERYDAY | 50%; ₹1,499 gives ₹750 discount and ₹749 total; ₹899 gives ₹450 and ₹449 |
| SAVE100 | ₹100 off a subtotal of at least ₹1,000 |
| EXPIRED10 | Expired offer; normal requests reject it |
| FIRSTBUY | First successful guest order, 10% capped at ₹500, one use per guest |
| LIMITED20 | 20% capped at ₹500, five successful uses globally, one per guest |
| FREESHIP | Valid zero-valued benefit because delivery is already free |

`POST /api/coupons/validate` accepts `{code,apply,expectedVersion,idempotencyKey}`. `apply:true` persists the valid selection; empty code removes it. Eligibility and expiry are checked again at checkout. Pure policy tests inject a clock; no public clock/reset endpoint exists.

## Checkout contract

Version2 requests require normalized name/email/phone/street/city/state/PIN, the expected cart version and an idempotency key. A legacy adapter preserves the five-field delivery request. The three existing demo methods remain card, PayPal and pay-later; each supports success, decline, cancel and timeout. No PAN/CVV/expiry is sent in an order request, stored in D1 or written to drafts.

Controlled forms preserve values across steps and background cart refresh. A thirty-minute tab draft stores delivery, step and safe confirmation identity/payload. Payment inputs stay in memory and require re-entry after an ordinary reload. An uncertain confirmation retains its exact payload/key; retry recovers the same order even if the server already cleared the cart. Receipt fields are validated before declaring success or removing the draft. Changed cart/coupon/stock/total requires review. Definitive decline, cancellation and simulated timeout leave the cart intact and create no order.

`GET /api/orders/:id` returns a receipt only to its owning guest. This supports confirmation recovery and does not implement P1 order history.

## Database and release safety

`drizzle/0001_resilient_commerce.sql` is an additive, registered migration with matching schema, snapshot and journal. It creates cart state, transient transaction guards, mutation/checkout receipt ledgers, coupon limits and redemptions. Existing tables/rows and migration0000 remain intact. Schema triggers increment revisions and enforce coupon use/eligibility constraints. A failing guard or constraint rolls back the D1 batch, including order/ledger/redemption/cart changes. There are no migration backfills or seed statements; legacy state is initialized lazily and the absent LIMITED20 configuration falls back to five uses.

Sites applies hosted migrations before uploading the Worker. Publishing therefore requires explicit approval of this source and schema change. Rollback can restore the previous Worker while leaving the additive schema in place; no destructive down migration is proposed. Automated P0-10 CI/release gates remain incomplete and need completion or an explicit release exception.
