# P0-07–09: API and test foundations

This slice adds REST adapters over the existing commerce service, local worker-owned
D1 fixtures, and a reusable Python pytest/Playwright framework. The legacy
`/api/shop` contract and the 13 original catalog records remain compatible. See
`docs/api/` for the versioned wire contract and `python-playwright/README.md` for
the test suite. No new production reset route or runtime test credentials exist.

## Local deterministic data

Build first, then run from the repository root:

```powershell
python scripts/build_qa.py
python scripts/test_data.py prepare --run-id demo-001 --worker main --port 8790
python scripts/test_data.py serve --run-id demo-001 --worker main
```

`prepare` is one command that initializes local Wrangler storage, applies every
SQL migration with an immutable SHA-256 ledger, and inserts deterministic fictional
guest fixtures. Repeating it is idempotent and does not clear existing test orders.
The ignored `.sites-runtime/test-data/demo-001/main/manifest.json` identifies the
owned database, URL, migrations and fixture recipes. It contains local-only guest
capabilities: do not upload it or copy it into evidence/source archives.

`build_qa.py` records runtime input and emitted artifact hashes in ignored
`.sites-runtime/qa-build.json`. `serve` verifies those bytes before starting the
Worker and records the config path, port, process ID, source/build identity and
timestamp in that namespace's `server.json`. The matrix runner verifies the
same build and records a real health readiness probe before each browser launch.
This binds local test results to the built Worker; it is not deployment proof.

Stop that server before resetting its namespace:

```powershell
python scripts/test_data.py reset --run-id demo-001 --worker main
```

Reset clears only that worker's local commerce tables, preserves schema and
migration history, and restores deterministic cart/coupon fixtures in one SQLite
transaction. It requires a matching local ownership manifest; it accepts no
remote URL, arbitrary path, SQL, Cloudflare account, or remote flag. Every command
uses local Wrangler or a SQLite file resolved under the owned root. Operations
hold an exclusive namespace lock; reset/prepare also reject a listening server
port. An abnormal OS kill may leave `operation.lock`; verify that server and
operation have stopped before manually removing that exact local lock file.

Create `gw0` on 8791 and `gw1` on 8792 for parallel processes. Each has its own D1,
coupon limits, cart revisions, orders and guest identities. A test's fresh browser
context further isolates its session. Never point two workers at a shared
namespace. Teardown closes browser contexts; reset is an explicit offline action,
so running tests cannot erase another worker's state.

Fixtures include `standard_guest` (product 46 quantity 1), `empty_cart_guest`,
`low_stock_product` (201, stock 2), `out_of_stock_product` (202, stock 0), and
`expired_coupon` (EXPIRED10). Inventory scenarios reuse the deterministic demo
records added in P0-02, separate from the 13 original IDs; inventory is static
application metadata, not a D1 table. No endpoint falsely claims to seed dynamic
inventory. Service failure scenarios use browser interception; coupon clock
boundaries use the existing pure-domain `CouponContext.now`, never a public
request-controlled clock.

## Migration and recovery

This slice adds no production schema migration. Prior 0000 and 0001 SQL/journal
entries are immutable. Local migration execution is transactional and verifies
stored checksums before reusing a database. Production rollback retains additive
tables; prefer a forward repair to destructive down migrations. Persisted cart
and order compatibility is checked in disposable databases. Retain sanitized
test evidence for review; local fictional database state can be removed after
the run is stopped and its resolved target has been verified. Never copy real
customer data into fixtures.

## Explicit remaining gates

Protected staging provisioning, staging seed/reset authorization, hosted staging
recovery and automatic CI deployment gates are not supplied by a local CLI.
They remain BLOCKED/NOT RUN until actual infrastructure and authorization exist.
No staging-only endpoint is exposed in production. Browser engine results must
be reported individually; a Chrome viewport run is not cross-browser or physical
device evidence. P0-10 and P0→P1 remain separate gates. Commit/push and deployment
require approval of the final candidate artifact.
